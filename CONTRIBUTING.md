# Contributing to ThinkFlow

ThinkFlow grows by people extending it **consistently**. The value of a methodology is that
two teams following it produce comparable results — so contributions must follow the same
patterns the existing exemplars establish. This guide is short on purpose; the patterns live
in the documents themselves.

## Ground rules

- **Documentation-first, tool-agnostic.** Never assume a specific AI tool. Refer to "your AI
  agent" and keep prompt examples provider-neutral.
- **Traceability is non-negotiable.** Every document declares what it consumes (Inputs) and
  what it feeds (Outputs). If a document doesn't trace to a problem, it doesn't belong.
- **Actionable over theoretical.** Prefer tables, checklists, decision trees, and diagrams to
  long prose. If a paragraph isn't changing what a reader *does*, cut it.
- **Show, don't assert.** New patterns land with a worked example, not just a description.

## The document header (every doc starts with this)

Put this block at the top of every methodology document so its role is unambiguous:

```markdown
> **Purpose:** one sentence — why this document exists.
> **Owner:** the human role accountable for it (e.g. Product Manager, Tech Lead).
> **Written:** at which lifecycle stage it is first created.
> **Changes:** what events cause it to be updated.
> **Inputs:** the upstream documents it consumes.
> **Outputs:** the downstream documents it feeds.
> **Dependencies:** other docs it must stay consistent with.
```

## Adding a lifecycle stage

Every stage document follows the **17-part stage anatomy** defined in
[`docs/methodology/stage-anatomy.md`](docs/methodology/stage-anatomy.md). The
[Requirements stage](docs/methodology/stages/requirements.md) is the reference implementation —
clone its structure, don't invent a new one.

1. Copy the section skeleton from `stage-anatomy.md`.
2. Fill in **all 17 sections**. If a section genuinely doesn't apply, say so explicitly rather
   than deleting it — a missing section reads as an oversight.
3. Add the stage to the index in [`docs/methodology/stages/README.md`](docs/methodology/stages/README.md)
   and confirm its Inputs/Outputs line up with the neighbouring stages in
   [`docs/methodology/lifecycle.md`](docs/methodology/lifecycle.md).

## Adding a template

Templates live in [`docs/templates/`](docs/templates/) and are **fill-in-the-blank**: real
headings with `<placeholders>` and short inline guidance in _italics_. A template should be
usable by copy-paste. Include a one-line "Inputs / Outputs" note so users know where it fits.

## Adding an agent role

Agent definitions live in [`docs/agents/roles/`](docs/agents/roles/) and follow the template in
[`docs/agents/agent-model.md`](docs/agents/agent-model.md): Purpose, Responsibilities, Inputs,
Outputs, Context Required, Documents Consumed, Documents Produced, and **Human Approval Gates**.
Every agent must name at least one human gate — AI executes, humans decide.

## Adding a workflow

Workflows live in [`docs/workflows/`](docs/workflows/) and follow
[`docs/workflows/workflow-spec.md`](docs/workflows/workflow-spec.md): a Mermaid flow diagram,
numbered steps, the documents touched, AI involvement, human checkpoints, and deliverables.
[New Feature](docs/workflows/new-feature.md) is the reference.

## Adding a worked example

Examples live in [`examples/<name>/`](examples/) and must document a project **end-to-end** using
the real templates, ending in an explicit traceability chain
(`PROB-n → US-n → AC-n → ADR-n → TASK-n → TEST-n`). The
[Todo example](examples/todo/README.md) is the reference.

## Style

- GitHub-flavored Markdown. Diagrams as ` ```mermaid ` fenced blocks so they render on GitHub.
- Sentence-case headings, tight sentences, US spelling.
- Prefer stable relative links between docs; don't hard-code absolute paths.

## Before you open a PR

- [ ] Doc header present and accurate.
- [ ] Inputs/Outputs resolve to real files (no dead links).
- [ ] If it's a stage, all 17 anatomy sections are present.
- [ ] If it's a pattern, a worked example demonstrates it.
- [ ] Mermaid diagrams parse (preview them).

## Commit conventions

Use clear, imperative commit subjects (e.g. `Add security-review stage`). Do **not** add AI
tool co-author or "generated by" attribution trailers to commits.
